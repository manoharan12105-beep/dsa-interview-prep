    What system design is

    A system is components working toward a common goal. Your digestive system was discovered; software systems are built, so we get to choose and improve their components as load grows.

    Remember2 min revise
    • System = components + a common goal. System design = choosing the right components and putting them in the right place.
    • Code that works for 10 users must keep working for 10 million at once.
    • Every fix creates a new problem: a load balancer can die, a cache can go stale, a replica can lag.
    • Alien Bank: faster code → vertical scaling → horizontal scaling → shared DB → load balancer.
    System

    Why it matters

    An app that works for 10 users must keep working for 10 million users at the same time. WhatsApp, YouTube, Instagram and Amazon all do.

    KThe $10 server and its three failures 1:44

    A photo-sharing app starts on one rented server holding the web app, the database and the uploaded photos. That's the right start. Then it's featured and 10,000 people arrive in a day.

    Failure 1 · CPU & RAM run out

    Pages go from 200 ms to 10 s. Add a second server, and a load balancer to direct traffic.

    Failure 2 · database overloaded

    Everyone asks for the same trending photos. Keep popular answers in fast memory: a cache.

    Failure 3 · the machine dies

    A disk fails: app down, photos maybe gone. A single point of failure. Fix with a DB replica and object storage (S3) for files.

    ✓
    Notice: the code never changed. System design is deciding where each piece lives and what each choice costs, because every fix brings a new problem (a load balancer can die, a cache can go stale, a replica can lag).
    Junior engineer

    Builds a defined feature: known input, known output.

    Mid-senior

    Given a problem; picks the approach and fits it into the system.

    Senior

    Designs the system itself and makes the technology choices.

    HLD vs LLD: pick your altitude

    High-level design is the zoomed-out blueprint. Low-level design is the code inside one box. Interviews test both, and answering at the wrong altitude costs you.

    Remember1 min revise
    • HLD = the zoomed-out blueprint: servers, databases, caches, queues and how requests flow.
    • LLD = one feature's code: classes, functions, data structures (e.g. the like button).
    • "Design Instagram" is HLD; "design the like feature" or "an in-memory cache" is LLD.
    • Say your altitude out loud first. Answering at the wrong altitude is a top reason candidates fail.
    High-level design · HLD

    The blueprint

    The big pieces (app servers, database, cache, queue, CDN) and how a request moves between them.

    • Where does a request go?
    • Where is data stored?
    • What breaks first when traffic grows, and how do we fix it?
    Low-level design · LLD

    One feature's code

    Zoom into the like button: which function runs, how to check the user already liked it, how to save it, how to update the count without counting anyone twice.

    Classes, objects, data structures.

    Interview questionAltitudeTalk about
    Design InstagramHLDComponents, data flow, trade-offs
    Design the like featureLLDFunctions, checks, data structures
    Design an in-memory cacheLLDClasses and data structures, no servers
    ✓
    Say this first: "I'll stay at the high level: components, data flow and trade-offs. We can zoom into any one component later." Interviewers rarely stop you; they just let you spend 20 minutes at the wrong height.
    Interview questions · 2
    CompareHLD vs LLD?HLD is the system blueprint (components and data flow); LLD is one feature's internals (classes, functions, data structures).
    ScenarioAsked to design an in-memory cache. Start with load balancers?No. That's LLD: talk classes and data structures, not servers.

    Functional vs non-functional requirements

    Functional = what the system does (features). Non-functional = how well it does them (speed, uptime, safety). Pin both down before drawing anything.

    Remember2 min revise
    • Functional = what the app does (features). Non-functional = how well (speed, durability, scale, uptime, cost).
    • Every component you add exists to meet a non-functional requirement. Users ask for a fast app, never a cache.
    • Before designing ask: how many users? read- or write-heavy? what can never be lost? how fast must it feel? what does it cost?
    • Justify every box later with an answer: "I'm adding a cache because reads dominate."
    Functional · Amazon
    1. Register, log in
    2. See, search and filter products
    3. Add to cart, apply coupons
    4. Place order, pay
    5. Track the order
    Non-functional · Amazon
    • Handle 1 million daily active users
    • Respond in < 200 ms per request
    • Be up 99.9% of the time (SLA/SLO)
    • Encrypt data
    • Survive 10× traffic on sale days (Diwali, Black Friday)
    • Be fault tolerant

    The generic non-functional checklist

    Scalability

    Scale vertically or horizontally when a server tops out.

    Availability

    Uptime promised in SLAs/SLOs. Break a written SLA and customers can sue.

    Reliability

    No data loss.

    Performance

    Latency targets: P90, P95, P99.

    Security

    Authentication, authorization, encryption; modular code.

    Observability

    Monitoring and logging after release.

    i
    Extra context. 99.9% uptime allows about 8.8 hours of downtime a year; 99.99% allows about 53 minutes. An SLA is the contract with customers; an SLO is the internal target.

    Data-intensive or compute-intensive?

    Ask this first. If the time goes into moving data, fix the data path. If it goes into calculating, fix the compute. Spending on the wrong one costs money and fixes nothing.

    Remember1 min revise
    • Time lost moving data → data-intensive (feeds, chat): fix DB, cache, network.
    • Time lost calculating → compute-intensive (rendering, ML): fix CPU/GPU, parallelism.
    • Judge per feature: YouTube serving = data, recommendations = compute.
    Data-intensive

    Moving lots of data

    • Examples: Instagram feed, WhatsApp messages, bank transactions, analytics dashboards, log processing
    • Worries: read speed, safe storage, many users at once, a server dying
    • Fix with: databases, caching, replication, sharding, consistency, CDNs
    • Instagram scales with many databases, aggressive caching, and a CDN for images (the DB stores only the file location)
    Compute-intensive

    Heavy calculation

    • Examples: image processing, video rendering, ML training, simulation, cryptography
    • Worries: compute speed, parallelism, compute cost, GPU vs CPU
    • Fix with: CPU/GPU power, parallel work, better algorithms
    • A flight simulator must behave exactly like the plane, so it's all compute
    ✓
    One app can be both. YouTube is data-intensive when serving videos and compute-intensive for recommendations. Judge each feature, not the whole app.
    !
    Instructor slip. WhatsApp is said to handle "2 to 10 million messages per day". Public figures put it at roughly 100 billion messages a day; the point (huge data volume) stands.
    Interview questions · 3
    ScenarioYour feed is slow. Upgrade CPUs?Probably not. A feed is data-intensive; look at DB queries, caching, network calls and server config.
    ConceptHow do you tell which type a feature is?Where is time lost? Data movement → data-intensive; calculation → compute-intensive.
    WhyWhy does the distinction matter?Components cost money; putting them on the wrong side burns budget without fixing latency.
    05Foundations▶ T 19:34

    The seven building blocks

    Every app shows data (images, video, audio, text). Each component exists to store it, reach it, or deliver it faster and more reliably.

    Remember1 min revise
    • Seven components: database, app code + APIs, client, cache, load balancer, message queue, monitoring.
    • Sync calls wait for a reply; async calls hand off work (via a queue) and move on.
    ① Database

    Stores and returns data. Two families: SQL and NoSQL.

    ② Application code + APIs

    Hides tables from users and exposes endpoints (GET /students) to insert, update, read and delete. Talks to the DB over HTTP/TCP/IP and speaks JSON.

    ③ Client application

    What normal users touch: web, mobile, even an ATM. Most requests start here.

    ④ Cache

    Keeps frequently used data close so we skip slow DB queries (say, a join across 12 tables).

    ⑤ Load balancer

    Checks server health and spreads requests across servers.

    ⑥ Message queue

    A broker for async work. An order service drops "send SMS" into the queue and moves on; the queue stores, delivers and retries.

    Sync call

    Wait for the other service's confirmation before moving on.

    Async call

    Hand the task off and continue without waiting.

    Interview questions · 3
    WhyWhy not let users query the database directly?Users don't know schemas or queries, and it's unsafe. The app layer hides complexity behind endpoints.
    CompareSync vs async calls?Sync waits for a reply; async fires the task and moves on (e.g. via a message queue).
    ConceptWhy do we need monitoring and logs?To see errors, their stack traces, and whether a new feature broke an old one.

    Monolith vs microservices

    Start with one codebase deployed as one unit. Split a piece into its own service only when it gives you a reason.

    Remember1 min revise
    • Monolith = one codebase, one deployment. Microservices = many small services talking over the network.
    • Start with a monolith: simple, fast for small teams, one log to read.
    • Split a piece out only for a reason: it needs independent scaling, or teams are blocking each other.
    • Most real companies run a monolith plus a few split-off services.
    Why the monolith is right at first
    • One codebase, one thing to deploy and test
    • Parts call each other directly; nothing to fail in between
    • One place to look when something breaks
    • Small teams move fast

    Downside: change the signup page and you redeploy everything.

    Two reasons to split
    1. Independent scaling. The feed needs 10 servers, uploads need 2. A monolith scales both to 10.
    2. Team size. 40 engineers on one codebase queue up and step on each other's changes.
    !
    Buzzword trap. The instructor has seen a 5-person startup run 30 microservices and spend more time debugging the network than building product. Debugging gets harder too: one request may touch five services' logs. Decide from requirements.
    Interview questions · 3
    CompareMonolith vs microservices?One codebase and one deployment, vs many small services deployed separately that talk over the network.
    WhyWhen would you split a service out?When it needs to scale independently (the read-heavy feed) or teams keep blocking each other.
    WhyDownsides of microservices?Network calls can be slow or fail, and debugging spans many services and logs.
    07Foundations▶ K 21:24▶ T 17:43

    Vertical vs horizontal scaling

    Two ways to get more power: a bigger machine or more machines. Use the first until it stops working, then the second.

    Remember1 min revise
    • Vertical = bigger machine. No code changes, but it has a ceiling, costs rise steeply and it's still one point of failure.
    • Horizontal = more machines. No upper limit and no single point of failure, but needs a load balancer and shared data.
    • Rule of thumb: scale up first, scale out when you hit the limit or can't risk one box.
    Vertical · scale up

    Buy a bigger machine

    • More CPU, RAM, faster disk; zero code changes
    • Hard ceiling: the biggest machine on the market
    • Cost isn't linear: 2nd-biggest → biggest can double the bill for ~20% more power
    • Still one machine: it dies, the app dies
    Horizontal · scale out

    Add more machines

    • 10 cheap servers instead of 1 giant; need more? add an 11th
    • No upper limit, no single point of failure
    • New questions: who routes traffic? (load balancer) Where does shared data live? (a shared DB)
    • How every large system actually scales
    ✓
    Interview answer. "Bigger server first: it's simple and buys time with zero code changes. But it has a ceiling and is one point of failure, so beyond that we scale horizontally." Add specifics: a 50-user internal tool stays vertical; a consumer app heading for a million users goes horizontal. Most systems end up using both.
    Interview questions · 2
    ScenarioYour app is slow. Why not just buy a bigger server?You can, first. But vertical has a ceiling, gets expensive fast and is still one point of failure; then scale out.
    WhyWhat new problems does horizontal scaling create?Routing traffic (load balancer) and shared state/data (a shared database and session store).
    08Communication▶ K 25:48▶ T 56:17

    How a request travels, and DNS

    Type a name, get a page: DNS, HTTPS and round trips. People use names; machines need IP addresses. DNS (Domain Name System) translates between them, spread across many servers.

    Remember2 min revise
    • Name → DNS → IP address → HTTPS request → server → response.
    • DNS lookup: resolver → root → TLD → authoritative name server; cached in browser, OS and resolver.
    • HTTPS (the S is a lock) stops anyone in the middle reading traffic.
    • Latency = time for one round trip. Bandwidth = pipe width. Feeds are slow from many round trips, not big files.

    KThe whole journey of one request 25:48

    1. User types photoapp.com. Machines need an IP address, the server's phone number.
    2. The phone asks DNS, the internet's phone book: "where is photoapp.com?" (with many servers, DNS returns the load balancer's IP).
    3. The phone sends an HTTPS request, "get me the home feed". HTTP is the shared language; the S is a lock, so someone on the same café Wi-Fi can't read passwords.
    4. The server does the work and sends back a response.
    Latency

    How long one round trip takes (request out, answer back).

    Bandwidth

    How much data fits through at once: the width of the pipe.

    ✓
    Why feeds feel slow: 30 small thumbnails fetched one by one across the planet = 30 round trips, even on fast Wi-Fi. Caches (skip the DB trip) and CDNs (answer from nearby) exist to fight round trips.

    TInside DNS

    Why not keep the list in the browser?
    • 350+ million domains would make every browser huge and slow
    • IPs change (move from GoDaddy to Google Domains) and every browser would need updating
    • One central server can't hold it either: if it dies, the whole internet dies
    Domain vs subdomain

    telusko.com is the domain, an umbrella. docs.telusko.com and courses.telusko.com are subdomains under it.

    All of them live in one zone on the authoritative name server.

    !
    Instructor slip. The video says "13 companies" (and once "30") own the 13 root servers. There are 13 root server identities (A–M) run by 12 organisations, served from well over a thousand physical instances worldwide.
    Interview questions · 5
    CompareLatency vs bandwidth?Latency is round-trip time; bandwidth is how much data flows at once.
    BasicWhat does the S in HTTPS give you?Encryption: people in the middle can't read the traffic.
    ProcessWalk through a DNS lookup.Resolver → root server (which TLD) → TLD server (which name server) → authoritative name server (the IP) → browser connects.

    APIs and the five API styles

    Swiggy, Uber and Ola don't build maps; they call Google Maps' API. An API (Application Programming Interface) lets other software use your features without touching your database.

    Remember1 min revise
    • APIs let others use your features without touching your database.
    • REST (JSON, many endpoints) · SOAP (XML, legacy) · GraphQL (one endpoint, ask for exact fields) · gRPC (protobuf, fast, microservices) · WebSockets (server can push).
    Use 1 · other applications

    A new app uses a movie site's ratings and review endpoints instead of re-collecting all that data. Direct DB access would be dangerous: they could delete data others rely on.

    Use 2 · your own front end

    A React web app and a Swift iOS app both call the same backend. They don't care what language the backend is in.

    REST requests and responses

    An endpoint = method + path. Paths name plural resources; methods say what to do; status codes say what happened.

    Remember2 min revise
    • Endpoint = method + path: GET /api/v1/users/1. Plural resource names.
    • PUT replaces the whole resource; PATCH changes only the fields you send.
    • Path for ids, query for filter/sort/search, body for sensitive or big data.
    • 200 · 201 · 204 · 301/302 · 400 · 401 (not logged in) · 403 (not allowed) · 404 · 500. Wrap arrays in an object.
    Method + pathDoes
    GET /usersList users
    GET /users/1One user
    POST /usersCreate (JSON body)
    PUT /users/1Replace the whole user
    PATCH /users/1Change some fields
    DELETE /users/1Remove user 1
    PUT vs PATCH

    User {id, name, username:"ash", age}. Send {username:"ak"}:

    • PUT replaces everything → name and age become null/default
    • PATCH changes only username

    Nesting, path, query or body?

    Path

    Only unique IDs or slugs: /blogs/what-is-java. Clear relationships nest: /blogs/7/comments, /users/3/comments.

    Query

    Filter, sort, search, paginate: /blogs?sort=desc, /blogs?q=java, colour and price filters.

    Body

    Anything sensitive or large: username and password on POST /login. Path and query are visible.

    POST /api/v3/users

  "age": 25

    JSON values

    Key–value pairs. Values can be a string, number, boolean, nested object, array or null.

    Relational (SQL) databases

    Restart a server and its memory is wiped, so data lives in a database. SQL databases (Postgres, MySQL) store entities as tables and link them with relationships.

    Remember2 min revise
    • Tables of rows and columns with a fixed shape; tables joined by keys.
    • Constraints: UNIQUE, NOT NULL, PRIMARY KEY, CHECK, FOREIGN KEY, DEFAULT.
    • Relationships: 1→N, N→1, N↔N (junction table), 1→1.
    • Transactions (ACID): delete a photo and its likes and comments together, all or nothing.

    Constraints

    UNIQUE

    No two rows share it: usernames on Instagram and Gmail.

    NOT NULL

    Must have a value: a first name.

    PRIMARY KEY

    Identifies exactly one row: id = 3 returns one record.

    CHECK

    Rules on values: password length > 8, phone is digits, name at least 2 letters.

    FOREIGN KEY

    A column pointing to another table's primary key: posts.author_id → authors.id.

    DEFAULT

    Filled in if not given: plan = "free", role = "student".

    Relationships 2:00:20

    KTransactions and ACID

    One unit of work

    Alan deletes a photo: remove the photo, its likes and its comments as one transaction. Either all succeed or none do, so you never keep likes on a deleted photo.

    Why the photo app picks SQL

    Every photo has the same fields (structured) and users, photos, likes and follows all join together. That points straight to SQL; the course picks Postgres. Joins answer "everyone Alan follows → their photos".

    i
    Extra context. ACID = Atomicity (all or nothing), Consistency (rules always hold), Isolation (concurrent transactions don't interfere), Durability (committed data survives crashes). The video names ACID but skips the letters.
    Interview questions · 5
    ConceptWhat is a transaction?A group of changes applied all-or-nothing, e.g. deleting a photo with its likes and comments.
    ComparePrimary key vs unique?Both forbid duplicates; the primary key is the row's identifier and is what foreign keys point to.
    ConceptHow do you model many-to-many?A junction table holding both foreign keys, e.g. students_courses(student_id, course_id).
    BasicWhat does a CHECK constraint do?Enforces a rule on values, like phone numbers being digits only.
    WhyWhy split video/audio/text into their own tables?One giant mixed table is slow to filter; a slim contents table plus one-to-one links stays fast.
    13Data & storage▶ T 2:08:34▶ K 50:43

    NoSQL, and when to pick it

    A blog's posts, comments, users and media already need six related tables. Relationships like that are hard to spread across many servers. "NoSQL" is like saying "not Java": many different kinds.

    Remember2 min revise
    • Structured + relationships + transactions → SQL (Postgres, MySQL). Flexible shape, huge scale → NoSQL.
    • NoSQL types: key–value, columnar, graph, document.
    • Real systems use both: Postgres for users/photos, MongoDB for preferences and behaviour.
    • Unsure? Start with SQL. Never say "NoSQL because it scales" without a reason.
    1 · Scales out easily

    Database indexes

    As rows grow into millions, queries slow down because the database checks every row. An index lets it jump straight to the right ones.

    Remember1 min revise
    • Without an index the DB scans every row. An index is the book's back-page index: jump straight to the rows.
    • Indexes speed reads but slow every write (the index must be updated too).
    • Don't guess: find slow queries first, then index those columns. Most tables have 3–5 indexes.
    • Photo app: index posted_by and upload_time.
    The symptom

    At 10k users the feed loaded in 200 ms; heading to millions it takes 500 ms.

    The cost

    Every insert must update each index too. Index everything and writes crawl.

    The method

    Start with none, find the slow queries, index those columns. Typical tables: 3–5 indexes.

    Caching: strategies and eviction

    The Telusko homepage shows 6 courses, each built from 4 sources (course, price, discount, info). That's 24 lookups per visitor. A cache keeps that answer ready.

    Remember2 min revise
    • Cache = small, very fast store for hot data. Redis answers in under 1 ms vs 20–30 ms from a DB.
    • Good entries are small, read constantly, changed rarely: trending posts, profile cards, sessions.
    • Keep it in sync with TTL (lazy, may be stale) or active invalidation (delete on change). Security data: invalidation only.
    • Watch for cache stampedes: stagger TTLs, let one request rebuild. Full cache → evict with LRU.
    • Strategies: read-through, write-through, write-around, write-back.

    KCache-aside with Redis 1:02:22

    TTL · lazy

    Entry expires (say 60 s) and the next request refetches. Users may see old data up to 60 s. Fine for follower counts.

    Active invalidation

    On change, write the DB and delete the cache entry right away. Fresh, but every write must remember to invalidate.

    Cache stampede

    A hot entry expires and 1,000 requests miss at once and hammer the DB. Defences: stagger TTLs (61 s vs 60 s, add randomness), let one request rebuild while others wait or get the old value, refresh hot entries before expiry.

    Load balancers

    One server tops out (say 128 GB is maxed), so you add more. DNS now returns the load balancer's IP, and the load balancer picks a server. It has two jobs: choose a server and check server health.

    Remember2 min revise
    • DNS returns the load balancer's IP; it forwards each request to a healthy server. It's just a server running software: a reverse proxy.
    • Health checks every few seconds; dead servers get no traffic.
    • Algorithms: round robin, weighted, least connections, least time, geo, IP hash. Real ones are hybrids.
    • Use Nginx, HAProxy or AWS ELB. Run more than one, or the load balancer becomes the single point of failure.

    KWhat a load balancer really is 29:44

    Not special hardware

    It's a server running software whose only job is forwarding each request. Anything that sits in front and takes requests on the servers' behalf is a reverse proxy; a load balancer is the most common kind.

    Health checks

    Every few seconds: "still alive?". Server 3 stops answering → within seconds it gets no traffic; the other nine absorb it and users never see an error.

    Off the shelf

    Nginx, HAProxy on your own machine, or a cloud one like AWS Elastic Load Balancer. Few companies build their own.

    It can die too

    One load balancer = all ten servers unreachable if it fails. Production runs several, with one taking over.

    K Least-connections example: S1 and S2 each got 7 requests, but S1 finished 3 (4 open) while S2 still has 7 open → the next request goes to S1. The load balancer keeps these counts itself.

    Stateless vs stateful servers

    Scale from one server to ten and users start getting logged out at random. The cause is state kept inside the servers.

    Remember1 min revise
    • Stateful = the server remembers things between requests in its own memory or disk (e.g. login sessions).
    • With many servers, sessions in local memory cause random logouts.
    • Fix: stateless servers + a shared session store (usually Redis). Servers become disposable.
    • Sticky sessions are a trap: uneven load, and sessions die with the server.
    • Test: "if this server vanished now, would a user lose anything?"
    Stateless tasks

    Upload a photo, download it, apply a filter, search, fetch details. The request carries everything; the server writes to external storage and forgets.

    Needs memory

    Login: the user must stay logged in between requests. That memory belongs in the shared store.

    Storing photos in a DB or S3 doesn't make a server stateful: that data lives outside it.

    Replication: copies of the same data

    Keep copies on several nodes. You get no single point of failure, higher availability, data close to users, and more read throughput (two copies ≈ double the reads).

    Remember2 min revise
    • Keep copies: typically 1 primary + 2 replicas. Reads spread across all; writes go only to the primary.
    • Replicas lag a few ms → eventual consistency. Read a user's own fresh data from the primary.
    • Primary dies → promote a replica (failover). Replication is not a backup: it copies your mistakes too.
    • Sync vs async; multi-leader (conflicts) and leaderless (quorum w + r > n) are advanced variants.

    KPrimary + replicas in practice 1:13:01

    Why only one writer

    Primary gets x = 9 while a replica gets x = 13. Which is true? Nobody knows. So writes go to the primary only; reads can go anywhere.

    Eventual vs strong consistency

    Replicas trail by milliseconds (replication lag): consistent eventually. Strong consistency = every read sees the latest write; simplest way is reading from the primary, which adds load back.

    The read-your-own-writes bug

    Alan uploads, refreshes half a second later, the read hits replica 2: no photo. It was never lost. Fix: his own recent reads go to the primary; everyone else can read replicas.

    Replication ≠ backup

    A bad DELETE wipes 1 M rows on the primary; replicas copy it within milliseconds. Keep backups: snapshots stored away from the system (restore Monday night's copy).

    Industry standard is two replicas (three copies). You pay for three, so use them: spread reads with a load balancer. If the primary dies, promote a replica: failover.

    TSingle leader, multi-leader and leaderless

    1 · Single leader

    Async · preferred

    + Fast, nothing blocked.
    − Users may read stale data from a follower for a moment.

    Sync · impractical at scale

    + Every follower is current; any can become leader.
    − Slow, and the resource stays locked while waiting.

    Adding follower F3
    1. Snapshot a node at, say, 12:55 pm
    2. Load the snapshot into F3 (hours)
    3. Snapshot the changes since 12:55 and apply them
    4. Connect F3 to the leader
    Leader dies
    1. Pick the follower with the newest timestamp
    2. Promote it to leader
    3. Point other followers at it

    Mentioned: FS image (full metadata snapshot) and edit logs (recent changes). Extra: these names come from Hadoop HDFS.

    2 · Multi-leader

    Each data centre has its own leader; leaders sync with each other. More tolerant and allows collaboration (two people on one Google Sheet), but conflicts happen: user 1 renames file A → B while user 2 renames A → C.

    Last write wins

    The later write (C) is kept.

    Higher ID wins

    Leader 11 beats leader 10, whoever wrote last.

    Ask the user

    Like a Git merge conflict: "keep B or C?"

    3 · Leaderless and quorum

    No leader: reads and writes go to several nodes at once (Dynamo, Riak, Cassandra, Voldemort). Don't wait for all of them: wait for a quorum, more than half.

    Partitioning (sharding): splitting the data

    When data won't fit on one node, or searches crawl even with indexes, split it. Two rules: all partitions together = the whole dataset, and load is spread evenly.

    Remember1 min revise
    • When data won't fit one machine, split it: each slice (shard) lives on its own database.
    • A shard key (e.g. user_id) decides where each row lives; simple rule = id % shards.
    • Problems: hot shards (celebrities together) and resharding (4→5 shards moves almost everything).
    • Consistent hashing moves only a small slice when you add a shard. Shard as late as possible.

    KShard keys and the resharding problem 1:19:34

    50 M users, billions of photos: replicas don't help, because each holds the whole dataset. Split it: each shard is one database machine holding a slice. Pick a shard key (user_id), then a rule. Simplest: shard = user_id % number_of_shards. Alan (10) → 10 % 4 = shard 2; user 13 → shard 1.

    Moved share computed over user ids 1–10,000. Consistent hashing is modelled as the ideal ~1/(new shard count).

    Hot shard

    Messi, Ronaldo and friends all land on shard 2 and it melts. Pick a shard key that scatters popular users across shards.

    Consistent hashing

    Each shard owns a range; a new shard takes one small range from one neighbour, so only those users move. Shard as late as possible (joins across shards are hard); MongoDB has sharding built in.

    By key range

    Users 1–50,000 → P1; 50,001–100,000 → P2. Simple, but if US users are in P2 and the app is big in the US, P2 gets 10,000 req/s while P1 gets 100.

    By hash of key

    hash(user id) decides the partition. Spreads better, but a flood to one partition still means rearranging.

    Message queues and pub-sub

    When someone buys a product, updating inventory is sync (the last item must go out of stock now). Email and delivery are async: fire and forget. A message queue holds the async work.

    Remember1 min revise
    • Async work (email, delivery, SMS) goes through a queue; sync work (inventory) doesn't.
    • Producers publish, consumers subscribe; pull or push; FIFO, unordered or priority.
    • Failures go to a dead letter queue; delete processed messages to avoid duplicates.
    • Skip queues for low traffic, real-time needs or when you need an instant acknowledgement.
    FIFO · strict order

    First in, first out. If #3 fails, the queue stops. Not recommended.

    Unordered

    Skip the failed one and keep going; it goes to the DLQ.

    Priority queue

    Priority 1 before 3 before 8 before 10, whatever the arrival order.

    Things the queue must handle
    • Order: only a priority queue gives any ordering
    • Consumption: consumers may pick requests in any order
    • Poison messages: bad requests that keep failing and waste resources
    • DLQ: dead letter queue for failures, reported back to the producer
    • Duplicates: delete a message once processed so it never runs twice
    Use vs avoid

    Use: async work, decoupling (analytics, logs), spreading load like a load balancer, deferred jobs (nightly reports, scheduled catalogue updates).

    Avoid: low traffic (queues cost money), real-time needs, or when you need an immediate acknowledgement.

    ✓
    Golden rule: if you can fire a request and forget it, it can be async. Examples: email, SMS, WhatsApp, broadcasts, OTPs (hence the 30-second timers).

    Three kinds of fault

    A fault is any time the system doesn't respond the way it should.

    Remember1 min revise

    Hardware · random

    The least reliable component, and the most powerful. Even AI-written code needs a human to be accountable.

    R4Revision

    Pairs people mix up

    HLD vs LLD

    System blueprint, vs one feature's classes and functions.

    Vertical vs horizontal scaling

    Bigger server (ceiling, one point of failure), vs more servers.

    Functional vs non-functional

    What it does, vs how well (latency, uptime, durability, cost).

    Monolith vs microservices

    One codebase and deploy, vs many services over the network.

    Stateless vs stateful

    Forgets between requests, vs keeps data in its own memory. Storing data in a DB doesn't make a server stateful.

    Latency vs bandwidth

    Round-trip time, vs pipe width.

    PUT vs PATCH · 401 vs 403

    Replace all vs change some · not logged in vs not allowed.

    Index vs cache

    Speeds finding rows inside the DB, vs skips the DB entirely for hot data.

    TTL vs invalidation

    Expire after time (maybe stale), vs delete on every change (fresh, more work).

    Write-through · write-back · write-around

    Cache then DB now · cache now, DB later · DB only, cache on read.

    Replication vs backup vs sharding

    Live copies (copy mistakes too) · off-system snapshots · data split across machines.

    Eventual vs strong consistency

    Replicas catch up in ms, vs every read sees the latest write.

    P in CAP vs partitioning

    Network split between nodes, vs sharding data.

    Load balancer vs message queue

    Routes live requests to servers, vs holds async work for consumers.
